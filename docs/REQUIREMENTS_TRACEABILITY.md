# Workbench requirements traceability

Last implementation audit: 2026-08-04 · PySFMEA 0.51.0 · analysis schema 0.6

This matrix traces the workbench acceptance criteria to executable implementation and
verification evidence. “Implemented” means a bounded capability exists and is tested;
it does not claim analysis completeness, certification qualification, or engineering
approval for a scanned repository.

| Acceptance criterion | Status and implementation evidence | Verification evidence |
|---|---|---|
| 1. Ingest a realistic Python repository and supporting artifacts | Implemented. Python is parsed semantically; tests, dependencies/locks, CI, containers/deployment, infrastructure, API/data schemas, migrations, documentation, static/test/coverage results, configuration, binaries, and unclassified material receive typed analyzed/indexed/excluded/unresolved/opaque accounting. | `repository_inventory.py`; scanner dependency/contract tests; coverage-accounting test |
| 2. Multiple deterministic adapters contribute normalized findings | Implemented. Specialized control/data/interface/concurrency/configuration/security/complexity/dependency/contract analyzers attach many-to-one provenance; a hashed ledger records status and exact entity IDs. | adapter contribution/ledger test; `adapter-runs.json` |
| 3. Incomplete context continues with explicit limitations | Implemented. Schema covers mission, boundary, modes/states, must-work/prohibited behavior, safe/degraded states, interfaces, humans, timing/resources, deployment, criticality, assumptions, exclusions, hazards, and profiles. | `system_context.py`; doctor/validation/report tests |
| 4. Bottom-up SFMEA and top-down SFTA are separate and reconciled | Implemented. Explicit gates/events remain human-authored; placeholders and bidirectional gaps do not invent causal sufficiency. | SFTA configuration, cycle/reference, correlation, diagram, validation, and report tests |
| 5. ## Authority boundary

No test above authorizes a risk decision. A passing tool suite establishes regression
evidence for the implemented software only. Project teams must independently establish
system context, hazard consequences, applicability, control adequacy, test oracles,
evidence sufficiency, residual risk, waiver/acceptance authority, and any required tool
qualification or certification credit.
