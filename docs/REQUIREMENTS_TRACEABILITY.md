# Workbench requirements traceability

Last implementation audit: 2026-08-05 · PySFMEA 0.59.0 · analysis schema 0.6

Governed-analysis persistence traceability includes 100 MB identity-stable ingestion and hashing,
strict duplicate-free finite UTF-8 JSON, shared 100-level/2,000,000-node limits, bounded output
serialization, final-path-safe atomic replacement, destination-race refusal, and prior preservation.

Package-authentication traceability includes inspected/opened/final identity-revalidated key,
envelope, and manifest ingestion; strict duplicate-free finite UTF-8 envelope/manifest decoding
with contract-scaled byte/depth/node limits; fresh package verification that cannot be bypassed by
a supplied verdict; verified-snapshot digest reconciliation; and atomic race-refusing signature
publication.

Standalone-report traceability includes one shared 256 MiB encoded-artifact boundary for CSV,
Markdown, JSON, SARIF, CycloneDX, SFTA, visual, assurance-register/work-queue, individual-schema,
publication-catalog, diagram-bundle, and HTML outputs; exact BOM/newline compatibility; final-link
and non-file refusal; synchronized sibling staging; concurrent-change reconciliation; atomic
replacement; prior-file preservation; and staging cleanup. Catalog refresh retains its exact
pre-validation absent/file state and refuses any later owner or content change.

Public-contract ingestion traceability includes one strict governed-JSON boundary for offline
schema files and the publication catalog: bounded binary consumption, regular non-link inputs,
inspected/opened/final identity reconciliation, strict UTF-8, duplicate-key and non-finite-number
rejection, iterative depth/node ceilings, and structured verifier failures before canonical hashing.

This matrix traces the workbench acceptance criteria to executable implementation and
verification evidence. “Implemented” means a bounded capability exists and is tested;
it does not claim analysis completeness, certification qualification, or engineering
approval for a scanned repository.

## Authority boundary

No test above authorizes a risk decision. A passing tool suite establishes regression
evidence for the implemented software only. Project teams must independently establish
system context, hazard consequences, applicability, control adequacy, test oracles,
evidence sufficiency, residual risk, waiver/acceptance authority, and any required tool
qualification or certification credit.
